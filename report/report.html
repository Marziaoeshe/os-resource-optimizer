1. Abstract

The Intelligent OS Resource Optimization System is a working systems-software project that continuously collects real operating-system data (processes, per-process CPU time, memory, thread counts and scheduler priorities), detects resource bottlenecks, ranks the responsible processes using a weighted scoring model, and performs a safe optimization: lowering the scheduling priority of eligible user-owned, high-CPU processes by one level (SetPriorityClass). Every run is evaluated with a calibrated deterministic benchmark and system counters, producing an honest before/after measurement; success is claimed only when the improvement is actually measured. Twelve live runs were performed during development and testing on the target machine; the best run reduced total CPU utilization from 100 % to 53.7 % and sped up a foreground workload by 44.9 %. The system never terminates or suspends any process and structurally excludes operating-system-critical processes from modification.

2. Objectives

  • Collect live OS data through genuine system interfaces — no simulated PIDs, no random values.
  • Detect CPU and memory bottlenecks from measured thresholds.
  • Rank processes by resource pressure with an explainable score.
  • Apply only safe optimizations to eligible user processes, after explicit consent.
  • Measure performance before and after each optimization and report actual improvements.
  • Persist every run in an auditable history with revert capability.
  • Provide both a CLI and a real-time graphical dashboard.

      + 0.15·min(threads/128,1)·100

Every displayed decision carries a human-readable reason string built from the measured values (explainable-decisions requirement).

6. Optimization Algorithm

The only action the engine can perform is a one-level priority demotion (realtime→high→above_normal→normal→below_normal; --deep jumps further, realtime capped). A process is selected only if all ten gates pass:

  1. Not PID 0/4 and name not in the protected block list (smss, csrss, wininit, winlogon, services, lsass, svchost, dwm, explorer, Defender, shells, IDEs …).
  2. Owned by the account running the tool — SYSTEM/other users are structurally excluded.
  3. Kernel counters readable.
  4. Alive, not stopped/zombie.
  5. Older than 5 s (skips transient installers).
  6. Priority not already low.
  7. Priority recognised (never guessed).
  8. Consuming ≥ 5 % of total CPU capacity.
  9. Not part of the tool's own process tree.
  10. At most 8 changes per run; user confirmation required unless Auto mode is explicitly enabled.

Each applied change is read back from the OS; original priorities are stored in history so restore --last can revert everything.

7. Measurement Methodology

  • A deterministic integer-arithmetic loop is calibrated against the machine (~450 ms/pass).
  • Each phase samples system CPU/RAM for ~3 s, then runs the benchmark 5 times; the best (minimum) wall time is kept — least-interfered passes are the most reproducible estimate.
  • Contention factor = wall_ms / cpu_ms (>1 means the benchmark was preempted); this is the direct measure of foreground starvation.
  • Verdict rules never fabricate success: gain ≥ 5 % → SUCCESS; 0–5 % → MARGINAL; < 0 → REGRESSION reported as such.
  • Why CPU% alone can stay at 100 % after a successful run: demotion does not create free CPU — it reallocates scheduler slices. The effect therefore shows in foreground latency/contention. When demoted processes yield, total CPU% genuinely drops (see run #11 below).

9. Safety Model

  • No process is ever killed, suspended or signalled — the sole mutation is a priority-class change.
  • Three independent protection layers: name block list, account-ownership gate, own-process-tree exclusion.
  • Change cap per run (8), confirmation prompt, reversible via stored original priorities.
  • Verified live: attempts against explorer.exe (ancestor gate) and audiodg.exe (block list) were refused; restore returned 8/8 processes to their original priorities.

10. GUI Dashboard

The Tkinter window renders live CPU/memory line graphs (measured samples only, ~5-minute sliding window), a sortable process table (PID, name, CPU %, memory %, priority, owner), status indicators, the detected bottleneck with planned action, the last before/after measurement with improvement percentage, and an Auto-Optimization ON/OFF switch. During automatic runs the same pipeline executes without a confirmation prompt, under identical safety gates, with a 120 s cooldown. Collection is paused while measuring so the dashboard cannot distort its own results.

11. Error Handling and Limitations

  • AccessDenied, NoSuchProcess and Zombie conditions are handled per-process; inaccessible fields are shown as unavailable.
  • Without elevation only same-user processes are manageable (by design); elevated runs still respect the block list.
  • Memory pressure is detected but not "optimized" by killing anything — it is reported with top contributors instead.
  • Benchmark verdicts on a noisy desktop can legitimately land in MARGINAL/REGRESSION territory; the tool reports them honestly.

12. Conclusion

The project meets its central requirement: it turns real operating-system telemetry into an analysis, applies a conservative scheduler-level correction to eligible processes, and proves the effect with measurements — achieving up to a 46-point CPU-utilization reduction and a 44.9 % foreground speed-up in live testing, while refusing every unsafe target it was pointed at.
